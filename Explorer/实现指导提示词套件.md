# 单英雄领地冒险 MVP 实现指导提示词套件

版本 0.1  
配套文档 GDD 单英雄领地冒险 MVP  
用途 指导代码代理分阶段制作可运行的游戏 MVP

## 1 使用方式

这套提示词不是一次性复制给模型的超长请求，而是一条连续的制作流水线。先使用提示词 0 建立共同上下文，再按编号执行后续阶段。每次只执行一个阶段；验收通过并保存项目状态后，再进入下一阶段。

每次新会话都要提供：

- 完整 GDD 文件。
- 本提示词套件。
- 当前项目目录或代码库。
- 上一阶段交付报告。
- 当前已知问题和用户新决定。

默认技术参数：

- 引擎：Godot 4.x。
- 语言：GDScript。
- 表现：2D。
- 战场：10 × 8 方格。
- 目标平台：Windows PC，键盘和鼠标。
- 设计分辨率：1920 × 1080，界面支持缩放。

若使用 Unity、Unreal 或其他框架，在提示词 0 中替换技术参数。不得因此改变 GDD 中的玩法规则、数据模型和验收标准。

## 2 所有阶段共同规则

把以下共同规则放在每一个实现提示词开头，或让执行代理明确确认继续遵守：

```text
你正在连续开发《单英雄领地冒险 MVP》。游戏设计的唯一基础是提供的 GDD 和用户最新明确决定。不要擅自扩大范围，不要恢复主城、多英雄、多阵营完整兵种树、联网或复杂随机地图。

开始修改前：
1. 阅读完整 GDD、当前项目说明、现有代码和测试。
2. 用简短清单说明本阶段会复用什么、修改什么、不会做什么。
3. 如果现有代码与 GDD 冲突，以用户最新决定和 GDD 的规则优先级为准；列出冲突并采用影响最小的修正。
4. 不得删除或覆盖与本阶段无关的用户修改。

实现时：
1. 保持规则逻辑与画面表现分离。
2. 使用稳定字符串 ID 和数据驱动配置。
3. 不把平衡数值散落在界面或场景脚本里。
4. 保持项目随时可以启动；不要留下无法编译的中间状态。
5. 随机结果必须使用可保存的种子和确定性随机流。
6. 新增功能必须有自动测试或可重复的验证场景。
7. 使用占位资源时，明确资源替换接口，不把占位尺寸写成规则。

完成前：
1. 运行本阶段测试和全部已有回归测试。
2. 实际启动项目，完成规定的正常流程验收，不使用开发者命令替代玩家流程。
3. 汇报新增与修改的文件、测试结果、仍存在的限制和下一阶段可依赖的接口。
4. 不要只给代码片段或建议；直接在项目中完成实现。
```

## 3 提示词 0 项目审计与实施蓝图

```text
目标：建立《单英雄领地冒险 MVP》的可靠实施基线。此阶段只做项目审计、必要的最小骨架和实施文档，不实现大块玩法。

输入：
- GDD 全文，尤其是第 18、19、21、22、23、25 节。
- 当前项目目录。
- 默认技术参数；如用户已指定引擎，以用户指定为准。

任务：
1. 检查项目是否为空、是否已有引擎工程、现有目录结构、启动入口、依赖、测试工具和版本控制状态。
2. 若项目为空，创建最小可启动工程；若项目已有内容，复用现有结构，不重复搭建。
3. 写出实施蓝图，列明：模块边界、核心实体、数据目录、场景或页面流、事件通信、随机数策略、存档策略、测试分层和调试工具入口。
4. 创建项目约定文档，确定命名、ID、数据验证、错误处理、日志和完成定义。
5. 建立一个可以自动运行的冒烟测试或最小测试入口。
6. 建立持续更新的实现状态表，按 GDD 验收项标记未开始、进行中、已验证、受阻。

不得做：
- 不实现完整地图、战斗、领地或事件系统。
- 不引入未经需要证明的大型第三方框架。
- 不为了未来扩展建立复杂抽象层。

验收：
- 项目可以启动并进入明确的占位主界面。
- 测试命令或测试入口可以运行并成功。
- 实施蓝图能把 GDD 的 12 个实现阶段映射到具体模块。
- 所有关键技术假设均被记录，没有隐藏的引擎选择。

交付报告必须包含：启动方式、测试方式、目录结构、主要接口、风险和下一阶段建议。
```

## 4 提示词 1 数据模型与内容验证

```text
目标：实现可供所有后续系统复用的领域数据、运行时状态和内容验证层。

重点 GDD：第 6、7、8、9、12、18、25 节。

实现：
1. 定义 GameState、Hero、Army、UnitStack、Territory、Encounter、Event、BattleState 的数据结构。
2. 定义英雄、兵种、技能、状态、装备、领地升级、事件和敌人的静态数据结构。
3. 所有实体使用稳定 ID；运行时实例另有 instance_id，二者不可混用。
4. 加入内容注册表和引用解析，能够按 ID 查询定义。
5. 加入内容验证器：检查重复 ID、缺失引用、非法属性、负成本、错误稀有度、不可达事件出口和无效生产配置。
6. 写入 MVP 的第一批测试数据：1 名英雄、8 种兵种的最小定义、4 种资源和领地三级结构。暂不要求完整技能数值。
7. 为数据结构添加序列化和反序列化测试，但此阶段不制作玩家存档界面。

边界情况：
- 定义被删除或改名。
- 编队数量为 0。
- 英雄不能被合并进 UnitStack。
- 神话单位占两个容量。
- 未知 ID 必须产生明确验证错误，不能静默生成空对象。

验收：
- 全部测试数据通过验证。
- 故意加入重复 ID 和缺失引用时测试会失败并指出位置。
- 数据序列化后再读取，关键字段完全一致。
- 英雄被明确建模为独立战斗单位，同时保留英雄独有字段。
```

## 5 提示词 2 存档 随机数与游戏状态

```text
目标：建立确定性游戏会话、状态切换和可靠存档，为后续系统提供可重复测试基础。

重点 GDD：第 18.3、25.2、25.3、25.4 节。

实现：
1. 新游戏创建 seed，并派生 world、event、battle、loot 四个独立随机流。
2. 实现世界地图、战斗、菜单三种顶层状态；只有当前状态接收玩法输入。
3. 实现 SaveGame 服务，包含 schema_version、game_version、content_version、seed 和必要运行时状态。
4. 实现手动存档、自动存档、读档、存档列表和可理解的错误提示。
5. 自动存档采用安全替换，失败时保留上一份有效存档。
6. 建立最小版本迁移接口和未知内容 ID 的处理策略。
7. 调试信息显示当前种子，并允许指定种子开始新游戏。

验收：
- 相同种子和输入得到相同随机序列。
- 调用战利品随机不会改变战斗随机结果。
- 保存、退出到主菜单、读取后状态一致。
- 损坏存档不会使游戏崩溃，也不会覆盖有效存档。
- 连续读取同一存档不会重复结算日期、资源或事件。
```

## 6 提示词 3 世界地图与探索纵切

```text
目标：制作第一条可玩的世界地图纵切，让玩家能从起点移动到一场遭遇和一个领地。

重点 GDD：第 4、5、16.1、21 节。

实现：
1. 创建手工配置的节点与方格混合地图，包含起始营地、道路、困难地形、资源点、遭遇点和一个领地。
2. 实现行动点：每天 10 点，地形按 GDD 消耗，交互和战斗预留对应成本。
3. 实现战争迷雾、英雄视野、已探索信息记忆。
4. 实现地点悬停信息、路径预览、预计行动点和不可达反馈。
5. 实现资源点采集和最小任务追踪。
6. 实现结束回合入口，但暂时只推进日期和恢复行动点；完整经济结算留给领地阶段。
7. 添加镜头移动、缩放、选中和返回英雄位置。

边界情况：
- 行动点不足时不能开始路径。
- 路径中途被新障碍阻断。
- 玩家快速连续点击不同目标。
- 菜单打开时地图不接受移动输入。
- 读档后战争迷雾和英雄位置一致。

验收流程：
新游戏 → 看到英雄和起点 → 预览并移动 → 消耗正确行动点 → 采集资源 → 发现遭遇和领地 → 结束回合 → 行动点恢复 → 保存并读取后位置与迷雾一致。
```

## 7 提示词 4 战斗核心纵切

```text
目标：实现一场可完整结束的 10 × 8 方格回合制战斗，暂时只使用英雄、民兵、盾卫和一个敌方单位。

重点 GDD：第 8.1、8.5、9.1、11、16.2 节。

实现：
1. 部署区与开战确认。
2. 单位速度排序和每轮行动序列。
3. 移动、近战攻击、防御、等待、反击和控制区。
4. 英雄作为独立单位进入同一行动系统，可移动、攻击、受伤和倒地。
5. UnitStack 数量、当前个体生命、总生命和伤亡换算。
6. 数据化伤害公式、攻防上下限和 0.9 至 1.1 的确定性随机浮动。
7. 攻击预览：预计伤害、预计击败数量、反击和命中条件。
8. 战斗日志和胜负结算。
9. 最小敌方 AI：选择合法目标并完成移动或攻击。

不得做：
- 暂不实现全部技能、远程、士气、复杂地形和首领机制。
- 不用动画回调决定伤害是否发生。

验收：
- 玩家可正常完成一场胜利和一场失败。
- 英雄倒地后若友军获胜，按 GDD 规则复苏并获得伤势。
- 所有友军失败时产生撤退或失败结果，不出现软锁。
- 攻击预览与实际结算在随机区间和显示规则内一致。
- 相同战斗种子和相同操作产生相同结果。
```

## 8 提示词 5 完整单位能力与战斗规则

```text
目标：把战斗纵切扩展为 GDD 规定的完整 MVP 战斗系统。

重点 GDD：第 8、9、11 节。

实现：
1. 远程攻击、射程、掩体、近身压制和高地。
2. 夹击、危险地形、推动和拉动。
3. 状态系统：持续时间、叠加规则、免疫、净化和战斗结束清理。
4. 士气趋势、溃逃、高低士气效果和 UI 解释。
5. 英雄三项战技：英勇突击、守护架势、决胜一击。
6. 8 种 MVP 兵种的核心特性，包括星界巨像的双容量和充能机制。
7. 治疗不能默认复活已损失个体。
8. 撤退、战后伤亡、经验、战利品接口和自动结算资格判断。
9. 改进战斗 AI，使其评分考虑伤害、击杀、风险、控制和目标价值；调试模式显示评分。

验收：
- 每种兵种都有一个自动测试和一个可启动的演示战斗。
- 英雄和兵种共享移动、目标、伤害、状态等基础规则，但英雄不会被合并为编队。
- 神话单位占两个军队容量且战场表现正确。
- AI 永远只选择合法行动，无合法攻击时会移动、防御或等待。
- 战后状态不会残留临时战斗对象。
```

## 9 提示词 6 英雄成长 装备与军队管理

```text
目标：实现英雄 1 至 10 级成长、四条短技能路线、装备和军队编成。

重点 GDD：第 8、9.4、15 节。

实现：
1. 英雄经验、等级、属性成长和技能点。
2. 统率、外交、征服、战技四条技能路线及前置条件。
3. 4 个装备栏和普通、稀有、传说品质；装备效果数据化。
4. 军队容量、编队加入、替换、解散和驻守接口。
5. 初始 4 个普通编队槽，统率最多提升到 6 个，英雄不占普通编队槽。
6. 伤势状态、领地治疗接口和英雄详情界面。
7. 战后经验与升级界面，不允许重复领取同一战斗经验。

边界情况：
- 升级时经验跨越多个等级。
- 装备被替换、存档中装备定义缺失。
- 军队已满时获得新兵种。
- 星界巨像需要两个空余容量。
- 英雄倒地时仍获得战斗经验，但不能触发需要亲手击败的条件，除非数据明确允许。

验收：
- 可通过正常战斗升至至少 3 级并选择技能。
- 技能实际改变对应系统行为，不只是界面文本。
- 军队超容量操作被阻止并给出解决选项。
- 装备、技能和伤势在保存读取后保持一致。
```

## 10 提示词 7 领地 经济与世界回合

```text
目标：实现无主城的领地经营、兵种生产和世界压力循环。

重点 GDD：第 5.4、6、7、21 节。

实现：
1. 金币、木材、矿石、奥术精华的统一资源钱包和交易记录。
2. 清除守军占领、条件购买、外交结盟三种领地取得接口。
3. 领地 1 至 3 级升级、资源产出、兵种产线、待招募池和容量上限。
4. 招募支付、亲临领地限制和驻军。
5. 两个 2 级以上领地之间的补给路线和受限快速旅行。
6. 每日结算顺序：产出、生产、威胁、袭击提示、动态刷新。
7. 威胁阈值带来的敌人强化和首领增益。
8. 没有完整战略 AI 时，以可预告的事件结算领地袭击。
9. 世界回合结算日志，防止重复结算。

验收流程：
占领领地 → 等待生产 → 招募兵种 → 升级领地 → 建立补给路线 → 快速旅行 → 防御或处理一次领地袭击 → 保存读取后全部状态一致。

必须测试：资源不足、待招募池已满、驻军为空、路线受威胁、连续快速点击结束回合、结算中途保存失败。
```

## 11 提示词 8 外交 征服与忠诚

```text
目标：实现两条都有价值的兵种吸收路径，并把结果连接到地图、战斗和军队系统。

重点 GDD：第 10、13.4、20 节。

实现：
1. 中立兵团态度：友善、中立、警惕、敌对。
2. 外交值计算和完全成功、部分成功、条件成功、失败、严重失败五种结果。
3. 交互前显示结果区间和主要正负因素，但不显示隐藏随机数。
4. 外交技能、区域声望、资源承诺和阵营偏好影响判定。
5. 战斗中的震撼值、士气崩溃和战后受降。
6. 归顺单位忠诚，以及胜利、补给和技能对忠诚的影响。
7. 残酷行为快速提高震撼但降低区域声望。
8. 同一遭遇不能同时获得完整外交与征服收益。
9. 增加统计记录，为平衡分析保存选择率和结果。

验收：
- 同一中立兵团可以通过至少两条不同流程被吸收。
- 外交失败不总是强制战斗，严重失败才可能先手攻击。
- 震撼来源能从战斗日志解释。
- 军队已满时成功加入不会丢失单位，玩家必须驻守、替换或放弃。
- 外交和征服结果在读档后不会重新掷骰。
```

## 12 提示词 9 事件 任务与稀有兵种

```text
目标：制作数据驱动事件系统和三条高级兵种获取内容。

重点 GDD：第 12、13 节。

实现：
1. 事件图结构：条件、文本、选择、成本、检定、结果、标记和后续节点。
2. 选择界面提前显示风险类别、成本和可见条件。
3. 英雄技能、装备、兵种、领地、声望和既有事件标记可解锁选项。
4. 任务追踪支持主线、支线、阶段目标和失败状态。
5. 实现至少 12 个可复用事件模板。
6. 实现战争傀儡稀有事件。
7. 实现狮鹫骑士多阶段传说事件链。
8. 实现星界巨像神话事件，包含获得单位与强化领地的终局选择。
9. 事件结果可以改变地图节点、资源、兵种、领地、声望和威胁。
10. 内容验证器检查无出口节点、无效引用、不可满足条件和重复奖励。

验收：
- 每条高级兵种事件能从正常地图流程触发并完成。
- 选择条件不满足时有明确说明。
- 事件中途保存读取后停留在同一已确定节点，不重复支付或奖励。
- 神话事件的二选一结果互斥且永久生效。
```

## 13 提示词 10 敌人 精英与最终首领

```text
目标：完成敌人内容、三个精英和两阶段最终首领，形成可通关主线。

重点 GDD：第 13、14、21 节。

实现：
1. 普通守军、游荡兵团和区域危险等级。
2. 沼泽吞噬者：多格占位和减速地形。
3. 叛军指挥官：鼓舞小兵并优先威胁英雄。
4. 镜像巫师：复制玩家最强普通编队的弱化版本，明确排除英雄、传说和神话单位。
5. 恐惧执政官两阶段战斗、控制核心、恐惧效果和区域威胁增援。
6. 主线情报可削弱首领控制技能，并在战前界面明确反馈。
7. 完整主线门槛和胜利结算。
8. 失败、撤退、重新挑战和最终战不允许撤退的规则。

验收：
- 三个精英机制都能从 UI 和战斗日志理解。
- 首领阶段切换不会重置错误的状态或复制奖励。
- 至少两种军队构筑能够在合理等级和资源下通关。
- 没有高级兵种仍可通关，但难度明显更高。
- 威胁值和主线情报都真实影响最终战，而非只改文字。
```

## 14 提示词 11 完整 UI 教学与可访问性

```text
目标：把所有已实现系统连接成玩家不依赖开发者说明也能完成的完整流程。

重点 GDD：第 16、17、21 节。

实现：
1. 主菜单、新游戏种子、继续、存档列表、设置和退出。
2. 世界地图 HUD、英雄详情、军队管理、领地、事件和任务界面。
3. 战斗 HUD、行动顺序、攻击预览、技能说明、士气趋势和战斗结算。
4. 首次游戏的情境教学：移动、采集、战斗、占领、招募、结束回合和保存。
5. 所有判定显示主要影响因素，永久决定二次确认。
6. 稀有度同时使用文字、图标和颜色。
7. 支持界面缩放、可重绑定输入、减少动画、音量分项和色觉友好模式。
8. 键盘与鼠标均可完成主要流程；焦点和悬停状态清晰。
9. 添加必要音效和可替换占位美术，优先保证反馈可读。

验收：
- 新玩家无需调试工具即可完成第一场战斗和第一次领地升级。
- 1920 × 1080 以及一个较低分辨率下无关键文字截断或按钮遮挡。
- 仅凭颜色无法区分的信息全部有第二种编码。
- 所有菜单返回路径明确，不会困在模态窗口。
```

## 15 提示词 12 平衡 调试与发布候选版

```text
目标：把功能完整构建提升为可重复测试、可交付的 MVP 发布候选版。

重点 GDD：第 19、20、21、25.6、25.7、25.8 节。

实现：
1. 完成调试面板：指定种子、资源、等级、兵种、传送、事件、战斗、AI 评分、日志和内容验证。
2. 记录 GDD 第 20 节的平衡指标，保存为本地测试数据；默认不上传。
3. 建立自动冒烟流程，覆盖新游戏、移动、战斗、占领、招募、保存、读取、结束回合和首领胜利。
4. 建立内容完整性检查和存档往返测试。
5. 用至少 3 个固定种子完成全流程测试，记录卡点、资源曲线、兵种使用和通关时间。
6. 调整数据而非写特殊例外，使普通、精英和首领胜率接近 GDD 目标区间。
7. 检查软锁、重复奖励、无限资源、无效事件、读档差异和无法返回的界面。
8. 清除调试残留、无用资源和阻断性日志错误，但保留开发构建调试入口。
9. 生成发布说明、已知问题、操作说明和内容清单。

完成条件：
- GDD 第 21 节十项验收全部有证据并通过。
- 3 个固定种子均可从新游戏正常通关。
- 自动测试全部通过，项目无阻断性错误。
- 正式构建无法误开调试面板。
- 已知问题不包含存档损坏、流程软锁、无法通关或规则结算不一致。
```

## 16 阶段修复提示词

当某阶段验收失败时，不要让代码代理重做整个系统。使用以下提示词：

```text
这是一次限定范围的修复，不是重构或新增功能。

失败的验收项：〔粘贴具体步骤、预期、实际结果和日志〕
首次出现版本：〔版本或提交〕
最近一次正常版本：〔若已知〕

请先复现，再定位最小根因。说明受影响的数据、规则和调用路径，然后实施最小安全修复。不要顺手改写无关系统，不要通过关闭测试、放宽断言或写死本次输入来让测试通过。

新增一个能在修复前失败、修复后通过的回归测试。随后运行该模块测试、相关集成测试和全部冒烟测试。最后汇报根因、修改文件、验证结果和仍可能受影响的边界情况。
```

## 17 规则变更提示词

当用户改变设计决定时，先评估影响再动代码：

```text
用户作出新的设计决定：〔粘贴决定〕

请对照 GDD 的规则优先级，先列出该决定影响的章节、数据结构、存档、界面、测试和既有内容。区分必须修改、建议修改和不受影响三类。若会破坏旧存档，提出最小迁移方案。

得到范围后直接实施必要修改，更新 GDD 和实现状态表，补充或更新测试，并完成正常流程验收。不要保留两套互相矛盾的规则，也不要让旧说明继续出现在界面或文档中。
```

## 19 执行顺序检查表

| 顺序 | 阶段 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| 0 | 审计与蓝图 | 有 GDD 和项目目录 | 工程可启动，测试入口可运行 |
| 1 | 数据模型 | 蓝图通过 | 数据验证与往返序列化通过 |
| 2 | 状态和存档 | 数据模型稳定 | 种子确定性和存档安全通过 |
| 3 | 世界地图纵切 | 状态服务可用 | 可移动、采集、探索和结束回合 |
| 4 | 战斗纵切 | 单位数据可用 | 一场战斗可正常胜负和结算 |
| 5 | 完整战斗 | 纵切稳定 | 8 兵种和完整规则可验证 |
| 6 | 英雄与军队 | 战斗接口稳定 | 成长、装备、编队管理可用 |
| 7 | 领地经济 | 世界回合稳定 | 生产、升级、补给和威胁闭环 |
| 8 | 外交征服 | 军队和战斗稳定 | 两条吸收路线完整 |
| 9 | 事件任务 | 状态与内容验证稳定 | 三个高级兵种路径可完成 |
| 10 | 敌人与首领 | 完整战斗和任务可用 | 主线可通关 |
| 11 | UI 与教学 | 所有系统可用 | 新玩家可独立完成核心流程 |
| 12 | 平衡发布 | 功能完整 | GDD 十项验收全部通过 |

任何阶段未满足退出条件，不应直接进入依赖它的下一阶段。可以先修复，也可以把无依赖的内容制作工作单独排期，但不能用后续功能掩盖当前基础故障。
